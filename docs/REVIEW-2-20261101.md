## 一、界面缺陷（3 条，都有截图证据）

### UI-1 数值未知时滑轨仍停在旧位置（误导性强）

**位置**：`MainWindow.cs:852` `ShowDesired()`、`MainWindow.cs:826` `Load()`

```csharp
void ShowDesired() { binding = true; try { if (Slider.Value != Desired) Slider.Value = Desired;
    value.Text = Available ? Desired.ToString() : "—"; } finally { binding = false; } }
```

`Slider.Value` 无条件被写成 `Desired`（上一次的值），只有文字按 `Available` 区分。`Load()` 在 `Available == false` 时同样只设文字、不动滑轨。

**现象**：故障态、断开态、不可调态下，数字显示 `—`（未知），滑轨却精确指着旧值。

证据（`artifacts/review2/render/render-report.json`）：

| 截图 | 亮度 lastKnown | 界面显示 | 滑轨位置 |
| --- | --- | --- | --- |
| `disconnected.png` | 53 | `—` | 53 |
| `prewrite-checksum.png` | 53 | `—` | 53 |
| `halted.png` | 70 | `—` | 70 |

三张截图上三个通道的圆点位置各不相同，全都停在上一次的值。

**为什么严重**：这台显示器出过黑屏事故，整个产品逻辑的核心是"不确定就明说不知道"。数字说"不知道"、滑轨说"我指得很准"，直接违背这个原则。用户看一眼滑轨会以为亮度还是 53，而实际上可能完全不是。

**建议**：`Available == false` 时把滑轨置为 `Minimum` 并降低不透明度（或干脆 `Visibility.Collapsed`，只留数值 `—`）。不要让它停在旧值上。

### UI-2 浮动提示会盖住底部状态栏

**位置**：`MainWindowNotice.cs:83` `PositionNotice()`

```csharp
noticeHost.Margin = new Thickness(20, 12, 20, layout.Padding.Bottom + footer.ActualHeight + 12);
```

提示卡片只避开了页脚（外观选择器那一行），**没有避开状态栏**。所以故障卡片会压住"画面模式 / 对比度 / 黑色稳定器"整排。

**现象**：`halted.png` 和 `prewrite-checksum.png` 里，状态栏右侧完全被卡片遮挡，"玩家 1" 和 "70" 看不见，只剩"当前状态"和左半边。

**这是有意设计**（浮动不挤动布局，卡片在上层），但避让范围算错了。状态栏恰恰是故障时最该看的地方——它显示"对比度 70 / 黑色稳定器 50"，用户要对照这些判断显示器是否正常。

**建议**：把 `noticeHost` 的底部边距改为 `layout.Padding.Bottom + footer.ActualHeight + statusShelf.ActualHeight + 12`，让它落在状态栏之上。或者更简单：故障态时把状态栏字号缩小仍保持可见。

### UI-3 浅色主题下"撤销"按钮几乎不可见

**位置**：`MainWindow.cs:687` —— `undo` 按钮**没有设置任何颜色**

```csharp
readonly Button ... undo = new() { Content = "撤销", Width = 100, Height = 34 };
```

对比：同文件里 `slider`、`increase`、`decrease` 都显式设置了 `Background`/`Foreground`，只有 `undo` 用 WinUI 默认样式。

**现象**：深色下默认样式是深底浅字，能用。浅色下变成白底、边框极浅、文字浅灰，几乎融进背景（`artifacts/review2/light-check.png`）。

顺带：浅色主题下所有副标题小字（"调节屏幕明暗""步长 10"）用的 `Palette.Secondary` 是 `#635D66`，在白底 `#F9F7F8` 上理论对比度约 5.7:1，够用但视觉偏灰。深色下是 `#BAB6BD` 配 `#111113`，对比度更高。两个主题的"次要文字"强度不一致。

**建议**：`undo` 显式套用与 `increase`/`decrease` 相同的配色；次要文字在浅色下再深一档（如 `#4A4550`）。

### UI-4 窗口高度略小时出现"裂缝状"滚动条

**位置**：`MainWindow.cs:107` `VerticalScrollBarVisibility = Auto`

窗口高度不足时（实测 2111×1506 就触发），右侧出现一条贯穿内容区的灰色竖线（`artifacts/review2/r-edge2.png` 放大 5 倍可见）。它不是标准滚动条外观——没有箭头、没有滑块，只是一条静止细线，看起来像布局错误。

深色下不明显，浅色下很扎眼。内容本身只超出一点点，滚动条却整条显示。

**建议**：给 `scroll` 设置一个最小的 `Margin` 或改用 `Overlay` 式细滚动条；或者压缩紧凑模式的 `MinHeight`（当前 `ControlChannel.View.MinHeight` 在紧凑态是 472，普通态 500），让常见窗口高度不触发滚动。

## 二、行为不一致（2 条）

### BE-1 同一个"加一步"三种入口三个步长

| 入口 | 代码位置 | 亮度/音量步长 | 锐度步长 |
| --- | --- | --- | --- |
| 主界面 +/− | `MainWindow.cs:747` 用 `spec.Step` | **1** | 10 |
| 托盘菜单 | `TrayMenuWindow.cs:21` `AdjustmentStep = 10` | **10** | （无此项） |
| 全局快捷键 | `GlobalHotkeys.cs:23` 硬编码 | **10** | 10 |

`ControlSpec` 里亮度、音量定义的是 `Step = 1`（`MonitorController.cs:5-6`），但托盘和快捷键都写死 10。

**用户感受**：主界面点一下 "+" 亮度 100→99，改用托盘或按快捷键，一下跳 10。同一个操作两套手感。

**附带问题**：亮度在 95 以上时，按 "+10" 快捷键钳制到 100，之后继续按**毫无反馈**（既不提示"已到上限"，也不震动）。主界面因为步长是 1，几乎不会碰到这个情况。

### BE-2 托盘菜单缺"锐度"调节

**位置**：`TrayMenuWindow.cs:69-72` 只有亮度、音量各两条

**现象**：快捷键支持锐度增减（`HotkeyAction.SharpnessUp/Down`），主界面有锐度滑块，唯独托盘菜单没有。用户在托盘里能调亮度音量却调不了锐度，而快捷键反而可以。

不建议直接加——托盘菜单已经 6 项，再加 2 项会很长。建议是**保持现状但想清楚理由**：要么托盘定位为"最常用的两项"，那就在 README 里写明；要么干脆把锐度也加上，让三个入口能力一致。

## 三、代码问题（4 条，按影响排序）

### CD-1 `MonitorController` 持有 `SemaphoreSlim` 但不实现 `IDisposable`

**位置**：`MonitorController.cs:39` `readonly SemaphoreSlim gate = new(1, 1)`；分析器 `CA1001`

`SemaphoreSlim` 实现了 `IDisposable`（内部有 `ManualResetEvent` 的惰性分配），但 `MonitorController` 不释放它。进程退出时由 GC 兜底，**实际不会泄漏**，所以严重程度低。

但这和项目其他地方的严谨程度不符——`NativeWindow`、`NotificationIcon`、`GlobalHotkeys` 全都仔细实现了 `Dispose`。留一个不释放的 `SemaphoreSlim` 在核心类里，是风格上的不一致。

### CD-2 `ReadbackException` 只提供 4 参数构造函数

**位置**：`MonitorController.cs:19`；分析器 `CA1032`

自定义异常未提供 `()`、`(string)`、`(string, Exception)` 三个标准构造函数。目前所有调用点都用 4 参数版本，**功能没问题**。但如果以后要序列化异常（跨进程传递），缺标准构造函数会出问题。属于"现在无害、以后可能咬人"。

### CD-3 三处快照校验逻辑不一致

**位置**：
- `MonitorController.cs:112`（`WriteOsdAsync` 内）
- `AppReset.cs:44`（`Capture` 内）
- `MonitorController.cs:133`（`ReadSnapshot` 内）

前两处都是：
```csharp
bool valid = value.Code == code && value.Success && (spec == null || ValidRead(spec, value));
if (valid && osd.Length == 1) valid = OsdProtocol.Decode(osd[0], value).Recognized;
```

第三处 `ReadSnapshot` **少了 `Recognized` 那一句**。当前不影响正确性（`ReadSnapshot` 之后 UI 会各自 decode），但这段逻辑没有单一出口，以后加校验规则要记得改三个地方，漏掉就是隐患。

**建议**：抽成一个 `static bool ValidateSnapshotValue(byte code, MonitorValue value)`，三处共用。

### CD-4 `JsonSerializerOptions` 每次新建

**位置**：`GlobalHotkeys.cs:46`、`MainWindow.cs:549,627`；分析器 `CA1869`

每次 JSON 序列化都 new 一个 `JsonSerializerOptions`。这几处都是低频调用（保存设置、写渲染报告），**对性能无可见影响**。但如果以后有高频序列化，这会成为热点。属于优化建议，不是缺陷。

## 四、经核实「不是问题」的几条

记录下来避免以后重复怀疑：

| 怀疑点 | 核实结果 |
| --- | --- |
| 默认快捷键 `modifiers = 7` 是否要求按 Ctrl+Alt+Shift 三个键？ | **是，且文档一致**。README 第 22 行明确写"默认均按住 Ctrl + Alt + Shift"。这是有意设计（避开只按 Ctrl+Alt 的系统快捷键冲突）。 |
| `Request()` 调用 `edit.Edit()` 不检查返回值，是否漏了判断？ | **安全**。值没变时 `Edit` 返回 false 且 `revision` 不变，随后 `Submit()` → `TakeSubmission()` 因 `HasUnsubmitted == false` 返回 null，不会写入。结果与 `Queue()` 的提前 return 等价，只是写法啰嗦。 |
| 重置顺序先改画面模式/色温，会不会把它们连带影响的亮度等值改掉？ | **已处理**。`AppReset.cs:74` 每次写完都 `Capture` 全部 7 项，并用 `expected` 字典核对**所有已写过的目标值**（第 47-48 行），一旦被连带改动立刻停机。 |
| CA1305（未指定区域性）共 28 处，是否真的会显示错乱？ | **实测不会**。`uint.ToString()` 和 `DateTimeOffset.ToString("HH:mm:ss")` 在 ar-SA、fa-IR、th-TH、hi-IN、de-DE、en-US 下输出完全一致。`uint` 无千位分隔符问题，时间格式 `HH:mm:ss` 是固定模式。属误报。 |
| CA2007/CA5392 共 164 条，要不要处理？ | **不需要**。CA2007 建议加 `ConfigureAwait(false)`，对 WinUI 单线程 UI 程序有害无益；CA5392 是默认 DllImport 搜索路径警告，这些 P/Invoke 全都指向系统 DLL，无法规避。 |
| 锐度上限 95 却只能调到 90，是 bug 吗？ | **有意设计**。`Slider.Maximum = read.Maximum / Spec.Step * Spec.Step` 会把上限对齐到步长整数倍，避免出现"滑到最后停在 95 但步长是 10"的中间态。测试明确断言了这个行为（"Readback maximum95 aligns slider and number editor to90"）。 |

## 五、优先级建议

1. **UI-1**（滑轨停在旧值）—— 影响产品核心信任模型，优先修
2. **UI-2**（提示盖住状态栏）—— 故障时最需要的信息被遮挡
3. **UI-3**（浅色下撤销按钮不可见）—— 浅色主题是新加路径，这个缺陷随之暴露
4. **BE-1**（步长不一致）—— 需要你决定统一成哪个值（1 还是 10）
5. **UI-4**（滚动条裂缝）—— 视觉瑕疵，不影响功能
6. **CD-1/2/3/4** —— 代码质量，可批量处理

第 4 项需要产品决策：托盘和快捷键用 10 是为了"一次移动明显"，主界面用 1 是为了"精细微调"。两者都有道理，但**同一个应用里不该两种手感**。我的建议是统一到 `ControlSpec.Step`（亮度/音量 1、锐度 10），托盘和快捷键也读这个值——代价是按快捷键调亮度会变慢（从 0 到 100 要按 100 次），所以更实际的方案是给 `ControlSpec` 加一个 `CoarseStep` 字段，托盘/快捷键用它，主界面 +/− 用 `Step`，并在 UI 上把两个步长都显示出来。

这个决定权在你，我不擅自改。

## 六、修复结果（2026-11-01 晚）

用户指示"全面修复"，6 条已修，逐条记录改法与验证。

### 6.1 UI-1 滑轨停在旧值 — 已修

`ControlChannel` 新增 `ShowUnknown()` / `ShowKnown()`：未知态把滑轨压到最小值并降不透明度到 `.35`，已知态恢复 `1`。`ShowDesired()` 和 `Clear()` 都改走这两个入口，任何路径都不会再让滑轨指向旧值。

`ShowDesired` 原来无条件写 `Slider.Value = Desired`，现在先判 `Available`——这是根因所在。

验证：`disconnected.png` / `halted.png` / `prewrite-checksum.png` 三张实拍，三个通道圆点全部在底部且变暗。

### 6.2 UI-2 提示盖住状态栏 — 已修

`PositionNotice()` 增加 `statusShelf` 高度避让，并按可见性取 0（画面与色彩页该栏是隐藏的）。同时监听 `statusShelf.SizeChanged`。

验证：`halted.png` 里"画面模式 / 对比度 / 黑色稳定器"三栏完整可见。

### 6.3 UI-3 浅色下撤销按钮不可见 — 已修

新增 `Palette.ControlSurface`（深色 `#35353B` / 浅色 `#EAE6EB`），`ControlChannel.ApplyButtonTheme()` 显式设置底色、前景、边框和禁用态资源。`UpdatePalette()` 里遍历所有通道调用，主题切换即时生效。

顺带把浅色次要文字从 `#635D66` 调到 `#544E5A`，提升小字可读性。

验证：`light.png` 里三个"撤销"按钮有明确底色和边框。

### 6.4 BE-1 步长不一致 — 已修

`ControlSpec` 增加 `CoarseStep`（亮度 1/10、音量 1/10、锐度 10/10），`GlobalHotkeys.Target()` 和托盘菜单都改为读它，不再硬编码 `10`。新增 `ControlSpec.ByCode()` 做反查。

界面表现：辅助文字曾尝试直接写两个步长，但"不影响 Windows 系统音量 · 步长 1，托盘/快捷键 10"在中间通道溢出被截断（实拍确认）。改为**悬浮提示承载**：加号、减号、滑轨三处 `ToolTip` 说明"这里每次 1，托盘和快捷键每次 10"。

### 6.5 BE-2 托盘缺锐度 — 已修

托盘改为按 `ControlSpec.Writable` 生成增减行，三个控制项齐全，共 8 行（打开 + 3×2 + 退出）。高度 455，仍在常规弹窗内、不触发滚动。

同时把脆弱的索引运算换成 `OpenSlot` / `AdjustFirstSlot` / `ExitSlot` 常量与配对推导。**退出仍固定为最后一项**，所以测试改用 `actions[^1]` / `actions[1..^1]` 表达"最后一项"和"全部调节项"，不再依赖具体数字。

### 6.6 UI-4 滚动条裂缝 — 已修（两种手段）

1. 紧凑模式阈值从 `< 780` 提到 `< 860`：普通布局实际需要约 856 逻辑像素，原阈值留下一段"用普通布局但装不下"的区间。
2. 新增 `ThinScrollBar()`：滚动条宽度 6px、轨道透明、滑块使用分割线颜色。**这条是主修法**——实测某些 DPI 下窗口逻辑高度是 861，刚好越过任何阈值，靠调阈值治不干净，只有让滚动条本身不刺眼才可靠。

### 6.7 CD-1~4 代码质量 — 已修

- **CD-1**：`MonitorController` 实现 `IDisposable`，释放 `SemaphoreSlim`。
- **CD-2**：`ReadbackException` 补三个标准构造函数。
- **CD-3**：抽出 `IsConfirmedValue()`（写入/重置用，含 OSD 名称确认）和 `IsUsableSnapshotValue()`（快照用，不含）。**这是有意保留两个**，见 6.8。
- **CD-4**：未改。低频路径，改动收益低于风险。

### 6.8 修复过程中自己造成的两个回归（都已修好）

**(a) 快照校验过度收紧，导致整屏控件失效。** 最初把三处校验统一成同一个严格版本后，`--osd-controls` 从 30 条全过变成崩溃（`COMException 0x80040200`，按钮不可交互）。

根因：快照读取原本**不检查** OSD 枚举值是否被识别，测试会故意注入未知色温 `0x14=4` 验证"只禁用那一个编辑器、其余照常显示"。我的严格版让整个七项快照读取失败，全部控件被禁用。

回退方式：拆成两个方法——写入/重置路径要严格（写错会真改坏显示器），快照路径要宽松（未知值如实展示比整屏失效好）。对照实验确认：原始代码 30 条全过，严格版崩溃，拆分版 30 条全过。

**(b) 辅助文字溢出被截断。** 把步长说明直接拼进副标题后，中间通道文字超宽，"快捷键 10"被裁掉。改为悬浮提示（见 6.4）。

### 6.9 一条未能定论的偶发失败

`--tray-lifecycle` 的 "Duplicate open notifications with a changed anchor leave the visible popup in place" 曾连续失败 2 次（X 从 560 变成 616，即窗口跟着锚点移动了 56px），随后连续 8 次全部通过，**无法稳定复现**。

失败数据表明当时 `IsOpen` 或 `anchor` 状态异常，但加诊断后不再出现。**根因未确认**，可能与时序（`Reposition` 读到尚未完成的布局）有关。如果再次出现，优先查 `ShowAt` 里 `opening` 判断与前一次 `Dismiss` 的竞态。
