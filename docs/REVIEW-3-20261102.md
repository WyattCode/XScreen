## 一、修掉的问题

### BUG-1 窗口最小高度不足，布局会崩（严重）

**位置**：`MainWindow.cs:152`、`MainWindow.cs:522`

`PreferredMinimumHeight` 还停在 **680**，但内容实际需要 **1010**：

```
窗口 680 时：可用 290px，通道要求 620px → 溢出 330px
```

这是我把通道高度从 500 提到 620 时漏改的。用户只要把窗口往小拖，滑轨就会被压扁——正是上一轮费力修好的问题从另一条路回来。

**修法**：两处都改为引用 `WindowStateStore.MinimumWidth/MinimumHeight`，以后不会再漂移。

### BUG-2 紧凑模式成了死代码（严重）

**位置**：`MainWindow.cs:183` vs `WindowStateStore.cs:14`

紧凑阈值原本是 `h < 860`，但窗口最小高度被锁在 1050——**永远进不了紧凑模式**，`Compact()` 整段代码不可达。

**修法**：阈值提到 **1010**（普通布局真实需求），最小高度 **900**，两者衔接无缝隙：

| 窗口高度 | 模式 | 实际需要 | 结果 |
| --- | --- | --- | --- |
| 900–1009 | 紧凑 | 818 | OK |
| ≥1010 | 普通 | 1010 | OK |

### BUG-3 托盘分组文字漏算锐度（中等）

**位置**：`TrayMenuWindow.cs:150`

```csharp
group.Text = brightness || volume ? "快捷调节" : ... : "快捷调节 · 当前不可用";
```

判断只看亮度和音量。如果只有锐度可用，文字显示"当前不可用"，但锐度那两行其实是能点的——**自相矛盾**。上一轮我已经发现这个问题，但因为当时锐度还没进托盘，影响小；这一轮锐度进来了，影响变大。

**修法**：改为遍历全部可写控件累积 `anyAdjustable`。

### BUG-4 撤销按钮 hover/pressed 状态闪错颜色（界面）

**位置**：`MainWindow.cs` `ApplyButtonTheme()`

只设了 `ButtonBackgroundDisabled`，没有覆盖 `ButtonBackgroundPointerOver` / `Pressed`。鼠标悬停时 WinUI 默认画刷接管，按钮闪一下不属于任何主题的颜色。

**修法**：补全 11 个状态资源（背景/前景/边框 × 常态/hover/pressed/disabled），新增 `ControlSurfaceHover` 和 `ControlSurfacePressed` 两个调色板颜色。

### BUG-5 紧凑模式下滑轨补偿量失效（界面）

**位置**：`MainWindow.cs` `Compact()`

滑轨加 `Margin(18,0,0,0)` 补偿模板偏置，但 `Compact()` 把宽度从 56 改成 48 时没同步。补偿量是**固定位移**不是比例，宽度变了中心又歪。

**修法**：`Compact()` 里重设同样的 `Margin`，并加注释说明它是常量位移。

## 二、代码质量

### 已修：`ReadbackException` 引入的可空性警告

上一轮加的标准构造函数把 `null` 位置传给 `MonetaryValue? actual`，全开分析器时报 4 个 CS8625。改为命名参数 `actual: null` 后消除。

### 经核实「不是问题」的几条

| 怀疑点 | 结论 |
| --- | --- |
| `ShowUnknown()` 把 `Slider.Value` 设成 Minimum，会不会误触发写操作？ | **不会**。`ValueChanged` 先判 `binding`，`Queue()` 里再判 `enabled`/`Available`/`binding`，三重保护。 |
| 外观索引 0/1/2 与 `ApplyAppearance` 的 switch 是否对得上？ | **对**。0=深色，1=浅色，2=跟随 Windows，与下拉框添加顺序一致。 |
| `InvokeAction` 重构后索引语义是否变了？ | **没变**。旧逻辑 `index is 1 or 3 → +Step`，新逻辑 `pair = index-1`、偶数加奇数减，逐项核对一致。 |
| 托盘菜单从 6 行增到 8 行，会不会溢出？ | **不会**。实测 `scrollH=0, viewH=439`，能完整放下。 |
| `--tray-audit` 曾出现 3 条导航失败，是回归吗？ | **不是**。是上一次构建的旧产物（菜单还是旧结构）。强制重建后连跑 4 次全过。 |

## 三、界面细节（建议，未改）

这些是观感问题，不属于缺陷，改不改看你：

**1. 滑轨上端空隙大于下端**
滑块在 100 时紧贴顶部，但在 0 时离减号按钮较远。因为轨道高度固定、滑块只在上半段移动。可以给滑轨加 `SliderPreContentMargin` 微调，但收益有限。

**2. 三个通道的“撤销”按钮宽度都是 116，但文字是两个字**
横向留白偏多。缩到 88 更紧凑，代价是三列视觉重量变轻。

**3. 大数字（96px）与下方滑轨之间的留白偏大**
数值行 110px，字只占 96px。减到 104 能多给滑轨 6px，但字形下沿会贴边——我试过压到 92，数字被裁了，所以现在留了余量。

**4. 状态栏“当前状态”与右侧三个数值块的基线不齐**
左侧是 20px 标题 + 12px 说明，右侧是 11px 标签 + 24px 数值，垂直居中基准不同。视觉上左边偏上一点。

**5. 背景斜线在最左和最右下角比较明显**
已经从 0.65 降到 0.4，但在纯黑区域仍可见。如果品牌上允许，可以再降到 0.3 或裁掉两侧。

## 四、测试改动说明

本轮改了一条测试，理由如下：

`--osd-controls` 里原本硬编码 `ResizeLogical(840, 680)`，这恰好是我把最小尺寸从 680 提到 900 后失效的前提。改为读取 `WindowStateStore.MinimumWidth/MinimumHeight`，这样以后调整最小尺寸时测试会自动跟随，不会变成维护负担。

同时把断言从"能滚动"（`ScrollableHeight > 0`）改成"不横向溢出"（最宽控件 ≤ 视口宽）——原本的语义里"必须出现滚动"其实不是目标，不溢出才是。
